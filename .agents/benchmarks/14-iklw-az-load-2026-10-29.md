## Executive summary

The first completed kitchen create took **21.593 s** and **20.354 s** from assistant turn start; mean **20.974 s** (the baseline: 21.381 s). The complete assistant turn took **53.153 s** and **69.501 s**; mean **61.327 s** (50.638 s). Model calls occupied **96.26%** and **94.78%** of those turns.

**The create tool takes 0.600 s and 0.612 s against the baseline's 2.010 / 2.150 s — 1.5 s less in both runs.** Both runs create at call 2 after the image and the kitchen skill at call 1 (3.826 / 3.045 s). The create call takes **17.137 s** and **16.667 s** (the baseline: 17.167 / 13.618 s), of which **9.661 s** and **7.934 s** pass before its first output, with 166 and 152 reasoning tokens; the first kitchen comes 0.4 s earlier in the mean, within the baselines' own spread of 5.1 s.

After the kitchen, run 1 does the baseline's work in **31.560 s**: the lookup of the handle colour with the backsplash attempt, which the library cannot calculate (8.088 s, 7.267 s of it before a first output), the black handles (2.992 s), a render (10.272 s, 8.226 s before its first output) and the answer (8.854 s). Run 2 spends **49.148 s** in seven calls: it sets the handle colour Black, which the library answers by switching the handle design to the curved bow handle 100, sends the rail handle 110, which switches the colour back to stainless steel, sets Black once more and keeps the bow, tries the backsplash, renders and answers — the library's coupling of handle colour and design, named in each result, costs the run three rounds. Both answers say that the backsplash is missing. These are request/response wall times, including network and provider work, not isolated server compute times. The first-kitchen milestone is successful create-tool completion: a conservative point by which the kitchen has been loaded into the plan, not a measured first painted GPU frame.

## How it was measured

A copy of [run-hi-mcp-prompt.js](../scripts/run-hi-mcp-prompt.js), written by the session's make-timing-runner.mjs, retained its normal prompt, usage, tool, plan and snapshot collection and added timestamp-only hooks with a Playwright init script (timing-init.js). No productive file was modified, and no response routing was used, so the browser's HTTP cache works as usual. The collector of the baselines is no longer on this machine; this one was rebuilt from the method their reports describe and validated on synthetic intervals and on one model turn without a tool before the runs.

- The assistant's existing diagnostics supply per-call response duration, time to first output, reference acquisition, first visible text, tokens, cache counters, request bytes and full-turn duration.
- Browser events mark turn start and end around onPlanningAssistantPrompt, each model fetch (start, response headers, the end of the stream read through a clone), each tool forward start and end through callExternalObjectAgentTool with its result bytes, every output part of the window, and in the planner frame every planner call of the tools: its start from its `[hi-mcp] call` log line, its end from the clearing of the call's own timeout.
- Browser timestamps use performance.timeOrigin + performance.now(), so the host and iframe share an epoch. Tables use seconds relative to assistant turn start. A model call ends when its response stream ends; its start is that end minus the SDK's response duration.
- Tool result sizes are UTF-8 bytes of JSON.stringify(result), including the MCP wrapper and base64 image content where present. They are not model tokens or compressed HTTP bytes.
- Nested planner calls are attributed by the queue: the tools run one after another in call order, a read tool calls the planner methods of its sections once each, and a plan-changing tool reads, runs one group operation and reads once after it. Every planner call of these runs was attributed. Nested planner time is included in tool time. Overlapping tools are counted once for wall time. Model/tool overlap is measured from intervals and subtracted once.
- Recorded run start is the runner's runSession start, after browser launch. The subprocess measurement also includes browser launch, output writing and browser/launcher shutdown.
- The runner waits until the library context lists articles before it sends the prompt, and the assistant reads the library before the first prompt itself; both reads calculate the article templates. The reads of the turn are therefore warm, as in the hosts. The planner's own price refresh is not captured by these hooks.

Both turns completed without provider/chat errors, retries or excluded attempts, and both saved a plan.

## How to read the step deltas

**Agent/model delta s** is how long the model call takes to return its decision, tool arguments or text. It includes the provider round trip and stream handling. **Tools delta s** is the time spent executing that step's tools, counting parallel calls once. **Total step delta s** runs from the start of the model call until its tools complete; the last step ends when the assistant turn completes. The difference includes local handling within the step. Small gaps between steps and the initial reads of the library reference and the plan state are outside these step totals.

The **Start s** and **End s** columns are timestamps measured from assistant turn start; they are not durations. In the detailed call tables, **Delta s = End s − Start s** is the duration of that individual call. Tool/planner tables retain milliseconds as additional detail.

## Measurement gaps and open work

- **First painted frame:** no GPU presentation/paint marker was captured. Create-tool completion is an upper bound for a loaded kitchen.
- **Provider internals:** model time combines network, queueing, input processing, reasoning, generation and SDK stream handling. Time to first output does not isolate prefill; response-header time does not isolate network RTT.
- **Tool internals:** the planner table separates planner access from the surrounding tool, but does not profile every filtering, projection, docking, library-calculation or kernel-load function. The planner's price refresh after a plan change is not captured.
- **Historical baselines:** the baselines ran in the morning of the same day on the planner 5fd409e84 and the library before the sink texts; no contemporaneous control of the base planner ran with this capture. The model-free check separates the bytes; the seconds are compared with historical runs.
- **Instrumentation overhead:** extra events, UTF-8 size measurement and the timeout hooks add unquantified overhead; all runs have the same hooks. The planner is a Vite development server; do not use the page-startup numbers as production cold-start numbers.
- **Sampling:** two runs establish a repeated measurement and show the variation of single calls. They do not establish a p95 or the cause of provider variability.
