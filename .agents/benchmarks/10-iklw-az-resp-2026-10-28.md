## Executive summary

The first completed kitchen create took **27.149 s** and **29.949 s** from assistant turn start; mean **28.549 s** (the baseline: 21.381 s). The complete assistant turn took **57.417 s** and **64.614 s**; mean **61.016 s** (50.638 s). Model calls occupied **93.13%** and **95.33%** of those turns.

**Both runs keep the seven calls of the baseline.** The system prompt carries the new sentence — 318 bytes more than the baseline's —, and the planner runs the calls of one response in the order sent, as the model-free check of the session shows. The model still sends the two finishing edits and the render one per response: call 3 looks up the handle values, calls 4 and 5 set the handles and try the backsplash — in opposite orders in the two runs —, call 6 writes a summary of 379 / 139 characters and renders, call 7 answers. Every argument of calls 4 to 6 was known when call 3 ended. The plan's criterion — at most five calls, the edits and the render from one call — is met in neither run.

The create call takes **20.215 s** and **20.063 s**, of which **12.838 s** and **13.095 s** pass before its first output (the baseline: 17.167 / 13.618 s); the first kitchen comes later than in the baseline, before the point the change can touch. After the kitchen the runs spend **30.268 s** and **34.665 s** (27.691 / 30.823 s). These are request/response wall times, including network and provider work, not isolated server compute times. The first-kitchen milestone is successful create-tool completion: a conservative point by which the kitchen has been loaded into the plan, not a measured first painted GPU frame.

## How it was measured

A copy of [run-hi-mcp-prompt.js](../scripts/run-hi-mcp-prompt.js), written by the session's make-timing-runner.mjs, retained its normal prompt, usage, tool, plan and snapshot collection and added timestamp-only hooks with a Playwright init script. No productive file was modified, and no response routing was used, so the browser's HTTP cache works as usual.

- The assistant's existing diagnostics supply per-call response duration, time to first output, reference acquisition, first visible text, tokens, cache counters, request bytes and full-turn duration.
- Browser events mark turn start and end around onPlanningAssistantPrompt, each model fetch (start, response headers, the end of the stream read through a clone), tool forwarding start/end through callExternalObjectAgentTool, every output part of the window, and every planner-method start/end in the planner frame with its [hi-mcp] log line.
- Browser timestamps use performance.timeOrigin + performance.now(), so the host and iframe share an epoch. Tables use seconds relative to assistant turn start.
- Tool result sizes are UTF-8 bytes of JSON.stringify(result), including the MCP wrapper and base64 image content where present. They are not model tokens or compressed HTTP bytes.
- Nested planner calls are attributed by the [hi-mcp] tool and call log lines; the two reads before the first request run in parallel and are told apart by their planner method. Tools a model response sends together run in the planner one after another; their planner calls would be attributed by that order, each plan-changing tool ending with its feedback or error line — no response of these runs sent two planner tools together, so the rule did not apply. Nested planner time is included in tool time. Overlapping tools are counted once for wall time. Model/tool overlap is measured from intervals and subtracted once; it is 0.000 s / 0.000 s here.
- Recorded run start is the runner's runSession start, after browser launch. The subprocess measurement also includes browser launch, output writing and browser/launcher shutdown. Its result is distinct from the recorded ready + chat + snapshot phases.
- The runner waits until the library context lists articles before it sends the prompt, and the assistant reads the library before the first prompt itself; both reads calculate the article templates. The reads of the turn are therefore warm, as in the hosts.

Both turns completed without provider/chat errors, retries or excluded attempts, and both saved a plan.

## How to read the step deltas

**Agent/model delta s** is how long the model call takes to return its decision, tool arguments or text. It includes the provider round trip and stream handling. **Tools delta s** is the time spent executing that step's tools, counting parallel calls once. **Total step delta s** runs from the start of the model call until its tools complete; the last step ends when the assistant turn completes. The difference includes local handling within the step. Small gaps between steps and the initial reads of the library reference and the plan state are outside these step totals.

The **Start s** and **End s** columns are timestamps measured from assistant turn start; they are not durations. In the detailed call tables, **Delta s = End s − Start s** is the duration of that individual call. Tool/planner tables retain milliseconds as additional detail.

## Findings and the evidence behind them

### 1. The sentence reaches the model; the calls stay one per response

The first request of every turn carries the developer item **25,651 bytes** long against the baseline's 25,333: the new sentence of the system prompt. The steps after the create are the baseline's, one tool each: run 1 looks up `mod_HandleColor`, `mod_HandlePosType` and `mod_CreateBacksplash` (call 3, 7.224 s), sets the handles (call 4, 3.887 s), tries the backsplash (call 5, 5.152 s) and renders (call 6, 6.609 s); run 2 looks up the two handle attributes only (3.797 s), tries the backsplash (5.296 s), sets the handles (3.966 s) and renders (12.286 s). Run 2's backsplash switch needed no lookup at all; its argument was known when the create ended. No response after the create sends two tools — while call 1 still sends the two skill requests together, so the model does send several calls in one response where it sees no dependence.

### 2. What the model waits for is not shown by the captures

The served text leaves three readings that keep the calls apart, none of them established by these runs. The new sentence lists "a correction" among the results to wait for, and every attribute edit can answer one: run 1's handle edit answered that the library switched the rail handle to the curved bow handle. The sentence of D119 asks to build the next change on the result of the last one. And the render follows a summary in both runs — 379 and 139 characters announcing the images —, so the render is the model's hand-over to its answer rather than a part of the edits. A reworded sentence would have to address the first two; the third is proposal 5 of the analysis.

### 3. The planner would have run the calls of one response in order

The model-free check of the session sent the baseline's create, then the backsplash edit, the handle edit and `get-plan-images` at once through `callExternalObjectAgentTool`, as the AI SDK sends the calls of one response: the planner ran the backsplash operation, answered its library error, ran the handle operation and then the snapshot, whose group view shows the black handles. The unit tests guard the same order through the pinned AI SDK. The path is not what keeps the calls apart.

### 4. Slower calls, the same work

The create call takes **20.215 / 20.063 s** (the baseline: 17.167 / 13.618 s), **12.838 / 13.095 s** until its first output (8.913 / 5.736 s), with 289 / 299 reasoning tokens (200 / 123) and 809 / 816 output tokens. Every request carries 105 input tokens more, the new sentence; that does not account for seconds. The first kitchen comes after 27.149 / 29.949 s, before the point the change can touch; the rounds after it take 30.268 / 34.665 s against 27.691 / 30.823 s with the same calls, run 2's render call 11.790 s. Two runs per build do not separate this from the provider's spread on the shared deployment.

### 5. The backsplash still fails in the library

Both runs enable `mod_CreateBacksplash`, and both get Error 14034, no entry in `tab_GrainDirectionSettings` for the backsplash. The change takes **136.6 / 124.4 ms**; the model rounds around it cost seconds. The open issue is [library backlog §10](../backlog/library-issues.md#10-backsplashes-the-library-cannot-calculate). Both answers disclose the missing backsplash.

### 6. The kitchen is the baseline’s

Both snapshots contain one **3,010 mm** kitchen centred on the left wall at [-685, -240, 0] with **rotationZ = 90°**, the row of the baseline: HK260, USTB60, UHS60, GSP, SUT60, OTB60, DU, OTB60, OTB60. ## Measurement gaps and open work

- **First painted frame:** no GPU presentation/paint marker was captured. Create-tool completion is an upper bound for a loaded kitchen; first visible geometry could appear earlier within the 1.656–2.349 s create.
- **Provider internals:** model time combines network, queueing, input processing, reasoning, generation and SDK stream handling. Time to first output does not isolate prefill; response-header time does not isolate network RTT.
- **Tool internals:** the planner table separates planner access from the surrounding tool, but does not profile every individual filtering, projection, docking, library-calculation or kernel-load function. Remaining tool time must not be renamed CPU assembly time.
- **Final text start:** first visible text refers to the first planning preamble; the end of the turn marks completion of the final answer. Final-answer text-delta start was not separately instrumented.
- **Startup attribution:** page/module/library/plan/assistant initialization, the runner's readiness read and the assistant's library read before the first prompt overlap inside the ready phase. They were not profiled individually.
- **Instrumentation overhead:** extra console events, UTF-8 size measurement and log delivery add unquantified overhead; both runs have the same hooks. The planner is a Vite development server; do not use these page-startup numbers as production cold-start numbers.
- **Sampling:** two runs establish a repeated measurement and show the variation of single calls. They do not establish a p95, a stable service-level expectation or the cause of provider variability. Another pair costs about 2 minutes and 1.2M input tokens, most of them read from the cache.
