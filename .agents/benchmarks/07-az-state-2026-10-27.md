## Executive summary

**The move comes in the first model call.** On the build with the plan state per turn the move test makes its `place-group` call in call 1 and its first plan change completes after **4.530 / 3.475 s** from the turn start (mean **4.003 s**), against **8.287 / 14.214 s** (mean **11.251 s**) in the two baseline runs on the build of 06, where call 1 reads the live sections, call 2 fetches the kitchen skill and call 3 moves; the turn ends after 7.173 / 6.030 s against 13.058 / 16.848 s, with 2 model calls against 4 and 160,064 / 160,068 input tokens against 327,800 / 327,804. **No model call of any run reads the live sections before the first change**: the creations fetch their skill in call 1 and create in call 2, as in 06 — the image runs after 33.368 / 30.149 s (mean 31.759 s; 06: 29.654 s), the text runs after 28.486 / 35.739 s in runs 2 and 3 (mean 32.113 s; 06: 30.287 s), both within the spread of 06 —, and the kitchens are those of 06. Text run 1 stalled: its first call, the skill fetch, waited 52.722 s for its first output (22 output tokens, no reasoning, the same input as the 2.3 / 2.2 s calls of runs 2 and 3), a provider tail event like the 65 s call of run 71 in the test session of 2026-10-27; its kitchen came after 81.639 s and the run is kept, a third repetition beside it. The plan state costs 4,822 bytes (the default room) and 12,106 bytes (the three-tall-units plan) per turn, read in parallel with the library reference in 17–27 ms. **The plan state per turn is accepted**: criterion 1 in every run (the move at call 1, no live read before a change), criterion 2 with the move 7.2 s earlier in the mean and the two runs outside the baseline's range, criterion 3 with the creations within the spread of 06 and the same kitchens, criterion 4 with the bytes and milliseconds above.

## How it was measured

The collector of report 06, regenerated from the current [prompt runner](../scripts/run-hi-mcp-prompt.js), records in addition the input items of every request body (role, bytes, the first characters): in the example page, the hook marks every fetch whose path ends in `/v1/responses` (start, response headers, the end of the stream read through a clone, request bytes, the `reasoning` object and the input items of the body), the tool bridge `callExternalObjectAgentTool` (start, end, result bytes) and every output part the window receives; in the planner frame, it wraps the seven planner methods of `window.RoomlePlanner` and timestamps the `[hi-mcp]` log lines. Turn start and end are taken around `onPlanningAssistantPrompt`. All marks are `performance.timeOrigin + performance.now()`. No response routing is used, so the browser's HTTP cache works as usual.

A hook check before the paid runs sent the move turn with an invalid key on the pinned build: the two bootstrap reads, their planner calls and the log lines were timed, and the one model request to the Azure endpoint — 353,180 bytes, its input the system instructions, the library reference (270,736 bytes), the plan state (13,639 bytes) and the user message, in that order — was rejected with HTTP 401, without inference.

All nine paid runs completed without provider or chat errors, retries or snapshot failures; no run is excluded. Text run 1's first call stalled for 52.7 s before its first output — the provider's tail, not an error —, so a third text repetition was run and is reported beside it. The backsplash calculation failure of the image runs is tool feedback, separate from chat success.

## How to read the step deltas

Start/End are seconds relative to the assistant turn start. Delta is elapsed time, rounded to three decimals; the elapsed-ms columns keep short calls. A model call ends when its response stream ends, measured through the clone; its start is that end minus the SDK's response duration, so the start is derived. Model duration includes transport, provider work and streaming. Tool wall time is the union of parallel intervals; the two bootstrap reads of a turn run in parallel before its first request. A nested planner call belongs to the tool of the last `[hi-mcp] tool` line before its own `[hi-mcp] call` line in the planner frame. Planner calls without such a line are the planner's own price refresh after a plan change, listed apart. A window update is any output part the window receives: a status (`activity`) or a piece of answer text. The first change is the `place-group` of the move and the `create-or-replace-groups` of a creation. Runner start follows browser launch; subprocess time includes launch and shutdown.

## Proposed experiments and rejected conclusions

- A creation gains no round from the plan state, because its first call still fetches the skill: that is the selector of proposal G, a backlog item for the choice of the models.
- The create call's reasoning varies from 238 to 401 tokens over the five creations here and from 219 to 332 in 06; whether the supplied state adds to it needs more repetitions than two or three. Not separable here.
- The provider stall of text run 1 is the tail every protocol has to leave room for: one call in 29 here, one in 411 in the session. A watchdog that resends a call without a first output after a limit would double the cost of a legitimate long reasoning; the tail is measured over more sessions first.
- The move test here starts from a plan with one group; the plan state of a large plan goes with every turn, also a question, and is not measured.

## Measurement gaps and open work

- Change completion is a conservative loaded-plan milestone, not the first painted frame; a window update is the output part the window receives, not its painted frame.
- Provider queueing, prefill, reasoning, generation, network and kernel or render work are not separated.
- First visible text is the planning preamble; the start of the final answer is not captured separately.
- The Azure deployment and the OpenAI series 01–05 are the same model on different deployments; their turns are compared for the shape, not for the seconds. The baseline for the creations is report 06 on this deployment; the baseline for the move is its two runs on the build of 06 in this session.
- Two repetitions per test give observed values and ranges, not a p95; the provider cache state differs between the runs.
