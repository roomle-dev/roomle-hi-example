## How it was measured

A scratch collector over [run-hi-mcp-prompt.js](../scripts/run-hi-mcp-prompt.js) retained the normal prompt, usage, tool, plan and snapshot collection. Existing assistant diagnostics record request sizes and sections. Temporary browser hooks mark model fetches, tool forwarding and nested planner calls. This document is rebuilt from those existing captures; no new model requests were made.

- Browser events use performance.timeOrigin + performance.now(); tables use seconds relative to assistant turn start.
- SDK start is derived from completion minus measured response duration. Model duration includes the provider round trip and stream handling.
- Tool result bytes are UTF-8 JSON.stringify(result), including MCP wrappers and base64 image content. They are not model tokens or compressed HTTP bytes.
- Nested planner ownership uses tool-start log order, method arguments and enclosing intervals. Interval unions count parallel work once. Model/tool overlap is measured separately.
- Recorded run start follows browser launch; full subprocess time also includes browser/launcher startup and shutdown.
- Readiness reads the article catalog before the prompt, making the measured in-turn library read warm. Browser response routing disables ordinary HTTP cache; instrumentation overhead is unquantified.

Both turns completed without provider/chat errors, retries or failed snapshot saves. Each contains one failed backsplash tool call, followed by an answer disclosing that omission. No kitchen repetition is excluded.

## How to read the step deltas

**Agent/model delta s** is how long the model call takes to return its decision, tool arguments or text. It includes the provider round trip and stream handling. **Tools delta s** is the time spent executing that step's tools, counting parallel calls once. **Total step delta s** runs from the start of the model call until its tools complete; the last step ends when the assistant turn completes. The difference includes local handling within the step. Small gaps between steps and the initial shared-reference preparation are outside these step totals.

The **Start s** and **End s** columns are timestamps measured from assistant turn start; they are not durations. In the detailed call tables, **Delta s = End s − Start s** is the duration of that individual call. Tool/planner tables retain milliseconds as additional detail.

## Findings and the evidence behind them

### 1. Model calls dominate the assistant turn

Model calls occupy **96.42% / 96.52%** of the turns. Initial plan/skill discovery takes **3.815 / 5.864 s**, reference discovery **13.731 / 12.467 s**, and creating the kitchen payload **10.800 / 12.396 s** before the create tool starts. The markers locate these costs at the model boundary; provider-internal causes remain unknown.

### 2. Information gathering is cheap locally; additional model rounds are expensive

Initial live-state and skill reads overlap and finish within **10.2 / 11.4 ms**. The mandatory planning-reference.md fetch takes **0.7 / 1.3 ms**, following a model decision lasting **13.731 / 12.467 s**. Warm bootstrap reference acquisition is about **15 ms**. The model-call and tool tables keep these durations separate.

### 3. Parallel tool wall time includes scheduling and serialization

After model call 4, attribute search, snapshots and plan context run in parallel. They occupy about **473.3 / 486.9 ms** of wall time, not the sum of their individual durations. Nested snapshot calls take **411.9 / 438.0 ms**; plan-state reads take only a few milliseconds. Outer read time must not be described as pure information-assembly CPU time.

### 4. Post-create work adds substantial latency, and the backsplash remains absent

## Measurement gaps and open work

- **First painted frame:** not captured. Successful create completion is a conservative loaded-plan milestone.
- **Provider internals:** queueing, prefill, reasoning, generation and network are not separately exposed. First-output wait is not isolated prefill.
- **Tool internals:** remaining tool time includes forwarding, scheduling, validation, projection and serialization; it is not isolated assembly CPU time.
- **Final text start:** first visible text is a planning preamble. Final-answer text start was not separately captured.
- **Startup:** initialization and the readiness catalog read overlap; page readiness is not a production cold-start measurement.
- **Cache and reference:** both first calls read 77,180 cached tokens. Cache state must be considered when comparing report 01.
- **Sampling:** two repetitions describe this observed range, not p95 or a service-level expectation.
- **Capture precision:** deltas use unrounded timestamps; displayed values are rounded, so subtracting printed start/end values may differ in the last digit.
