## Executive summary

**The change measured here is reverted.** It implemented two narrow pieces of [section 7 of the remaining-work analysis](../refactoring-analysis/planning-assistant-performance-next-steps.md#7-not-proposed) — the shortening of descriptions written on the line of their section name and `articleIds` on `get-plan-context` —, not the refactoring that section describes, which has not yet been tried properly. roomle-ui c13969005 reverts it. This report measures that attempt only.

The first completed kitchen create took **19.089 s** and **20.988 s** from assistant turn start; mean **20.039 s** (the baseline: 21.381 s). The complete assistant turn took **62.201 s** and **43.563 s**; mean **52.882 s** (50.638 s). Model calls occupied **94.56%** and **92.84%** of those turns.

**Every request carries 2,587 input tokens less, and the turn keeps the shape of the baseline.** The shared reference is 11,134 bytes smaller: the shortened descriptions, less the sink texts the library added since the baseline. Both runs make the baseline's seven calls — the two skills, the create at call 2, the handle lookup, the handle edit, the failing backsplash attempt, the render and the answer —, and no call reads the catalog: neither `articleDescriptions` nor `articleIds` occurs. The kitchen stands where the baseline's stood, in its finishes; in both runs a door unit takes the place of the baseline's dishwasher beside the sink, as in the photo.

The create call takes **14.054 s** and **15.542 s**, of which **7.069 s** and **8.650 s** pass before its first output (the baseline: 17.167 / 13.618 s). After the kitchen the runs spend **43.112 s** and **22.574 s** (27.691 / 30.823 s) with the same calls. These are request/response wall times, including network and provider work, not isolated server compute times. The first-kitchen milestone is successful create-tool completion: a conservative point by which the kitchen has been loaded into the plan, not a measured first painted GPU frame.

## How it was measured

A copy of [run-hi-mcp-prompt.js](../scripts/run-hi-mcp-prompt.js), written by the session's make-timing-runner.mjs, retained its normal prompt, usage, tool, plan and snapshot collection and added timestamp-only hooks with a Playwright init script. No productive file was modified, and no response routing was used, so the browser's HTTP cache works as usual.

- The assistant's existing diagnostics supply per-call response duration, time to first output, reference acquisition, first visible text, tokens, cache counters, request bytes and full-turn duration.
- Browser events mark turn start and end around onPlanningAssistantPrompt, each model fetch (start, response headers, the end of the stream read through a clone), tool forwarding start/end through callExternalObjectAgentTool, every output part of the window, and every planner-method start/end in the planner frame with its [hi-mcp] log line.
- Browser timestamps use performance.timeOrigin + performance.now(), so the host and iframe share an epoch. Tables use seconds relative to assistant turn start.
- Tool result sizes are UTF-8 bytes of JSON.stringify(result), including the MCP wrapper and base64 image content where present. They are not model tokens or compressed HTTP bytes.
- Nested planner calls are attributed by the [hi-mcp] tool and call log lines; the two reads before the first request run in parallel and are told apart by their planner method. Tools a model response sends together run in the planner one after another; their planner calls would be attributed by that order, each plan-changing tool ending with its feedback or error line — no response of these runs sent two planner tools together, so the rule did not apply. Nested planner time is included in tool time. Overlapping tools are counted once for wall time. Model/tool overlap is measured from intervals and subtracted once; it is 0.000 s / 0.000 s here.
- Recorded run start is the runner's runSession start, after browser launch. The subprocess measurement also includes browser launch, output writing and browser/launcher shutdown. Its result is distinct from the recorded ready + chat + snapshot phases.
- The runner waits until the library context lists articles before it sends the prompt, and the assistant reads the library before the first prompt itself; both reads calculate the article templates. The reads of the turn are therefore warm, as in the hosts.

Both turns completed without provider/chat errors, retries or excluded attempts, and both saved a plan.

## How to read the step deltas

**Agent/model delta s** is how long the model call takes to return its decision, tool arguments or text. It includes the provider round trip and stream handling. **Tools delta s** is the time spent executing that step's tools, counting parallel calls once. **Total step delta s** runs from the start of the model call until its tools complete; the last step ends when the assistant turn completes. The difference includes local handling within the step. Small gaps between steps and the initial reads of the library reference and the plan state are outside these step totals.

The **Start s** and **End s** columns are timestamps measured from assistant turn start; they are not durations. In the detailed call tables, **Delta s = End s − Start s** is the duration of that individual call. Tool/planner tables retain milliseconds as additional detail.

## Findings and the evidence behind them

### 1. Every request carries the shortened catalog

The shared reference is **11,134 bytes** smaller than the baseline's and the library reference **11,162 bytes** smaller. Every request of both runs carries **2,587 input tokens** less: the first call 67,960 against 70,547, and each later call by the same amount. Over the turn the runs send 571,896 / 571,725 input tokens against 587,868 / 590,942. The difference is the shortening less the library's additions (11,010 against 585 bytes of raw JSON); the tokens of the two are not measured apart. Of those input tokens 95.73% / 97.89% come from the cache, against 98.03% / 97.92% in the baseline.

### 2. The turn keeps its seven calls; no call reads the catalog

Both runs make the baseline's calls in the baseline's order: call 1 fetches the image and the kitchen skill, call 2 creates the kitchen, call 3 looks up `mod_HandleColor`, `mod_HandlePosType` and `mod_CreateBacksplash`, call 4 sets the handles, call 5 tries the backsplash, call 6 renders and call 7 answers. No model call requests `get-plan-context` (0 / 0): the sentence that now names `articleIds` beside `articleDescriptions` adds no detail read before or after the create. The model-free check shows the parameter working on the same planner and through the pinned embedding-lib: the ten articles of the walnut baseline's create in their order, an unknown id in `notFound` with the hint, and **8,153 bytes** of full descriptions for those ten against **86,703 bytes** for the whole catalog.

### 3. A door unit replaces the dishwasher beside the sink

The kitchen is the baseline's row in the baseline's place: one **3,010 mm** group centred on the left wall at [-685, -240, 0] with **rotationZ = 90°**, Classic fronts in Olive green 160, the oak decor 224, black handles. One article differs in both runs: the base unit between the hob and the sink is UTB60, a unit with one door and shelves, where the baseline had GSP, the dishwasher housing. The photo shows a door front there and no dishwasher, so the choice matches the image at least as well. Both changes of this capture touch the sink unit beside it: its catalog line is one of the 19 shortened descriptions, and the library's new SUT60 text puts the drainer over the unit on its left — that unit — and says to put a base unit there. The group views show the drainer over the door unit, as in the photo; the runs do not tell which of the two changes made the choice.

### 4. The seconds stay within the spread of the series

The create call takes **14.054 / 15.542 s** (the baseline: 17.167 / 13.618 s), **7.069 / 8.650 s** until its first output (8.913 / 5.736 s), with 127 / 124 reasoning tokens (200 / 123). The first kitchen comes after 19.089 / 20.988 s against 23.913 / 18.850 s. Run 1 then spends 43.112 s after the kitchen with the same five calls run 2 makes in 22.574 s: its calls wait 7.202, 5.575, 5.674, 9.077, 7.054 s for their first output with 40, 71, 92, 135, 133 output tokens, run 2's 2.660, 2.959, 4.043, 2.877, 2.140 s. Benchmark 10 measured create calls waiting 5.7 to 13.1 s for their first output on the same fixtures. 2,587 cached input tokens less per call do not account for a difference of that size, and two runs do not separate it from the provider's spread.

### 5. The backsplash still fails in the library

Both runs enable `mod_CreateBacksplash`, and both get Error 14034, no entry in `tab_GrainDirectionSettings` for the backsplash. The change takes **149.6 / 124.1 ms**; the model rounds around it cost seconds. The open issue is [library backlog §10](../backlog/library-issues.md#10-backsplashes-the-library-cannot-calculate). Both answers disclose the missing backsplash. The handle edit answers, as in the baseline, that the library switched the rail handle to the curved bow handle.

## Measurement gaps and open work

- **First painted frame:** no GPU presentation/paint marker was captured. Create-tool completion is an upper bound for a loaded kitchen; first visible geometry could appear earlier within the 1.778–1.788 s create.
- **Provider internals:** model time combines network, queueing, input processing, reasoning, generation and SDK stream handling. Time to first output does not isolate prefill; response-header time does not isolate network RTT.
- **Tool internals:** the planner table separates planner access from the surrounding tool, but does not profile every individual filtering, projection, docking, library-calculation or kernel-load function. Remaining tool time must not be renamed CPU assembly time.
- **Final text start:** first visible text refers to the first planning preamble; the end of the turn marks completion of the final answer. Final-answer text-delta start was not separately instrumented.
- **Startup attribution:** page/module/library/plan/assistant initialization, the runner's readiness read and the assistant's library read before the first prompt overlap inside the ready phase. They were not profiled individually.
- **Instrumentation overhead:** extra console events, UTF-8 size measurement and log delivery add unquantified overhead; both runs have the same hooks. The planner is a Vite development server; do not use these page-startup numbers as production cold-start numbers.
- **Sampling:** two runs establish a repeated measurement and show the variation of single calls. They do not establish a p95, a stable service-level expectation or the cause of provider variability. Another pair costs about 2 minutes and 1.1M input tokens, most of them read from the cache.
- **Library change:** the library changed between the baselines and this capture (see [What changed besides the code](#what-changed-besides-the-code)). The token difference is measured as a sum; no control run of the old planner on today's library separates the two changes in tokens, seconds or the articles chosen.
