# Feature Analysis: Isolate HI MCP Chat Windows

**Date:** 2026-10-03
**Status:** Implemented (local ownership verified; cloud deployment not yet verified)

## Requested Behavior

Two ligna-store tabs opened with the **same Cloudflare `mcp_server` URL and no extra parameters** must each control their own planner. When an example started by `npm run plan:gpt5.4` already occupies the local MCP server, a second store tab must **not** control that example's planner: its chat must be disabled with a visible, specific error. An unreachable or incorrect MCP URL must also produce a useful error in the chat window.

## Reproduction and Cause

1. Two store tabs using the same Cloudflare URL omit `mcp_session`. The store's `resolveMcpUrl` and browser bridge use the session only if supplied (sibling repo `ligna-store/hi-mcp/chat-options.ts:38-41`, `ligna-store/hi-mcp/browser-bridge.ts:56-71`). Both `/mcp` and `/bridge` therefore reach Cloudflare's `default` container ([worker.ts:11-22](../../hi-mcp/cf/src/worker.ts#L11-L22)). Each container runs a Node server with **one** active `PageBridge`. Every new page `hello` replaces the old page and rejects its pending calls ([server.ts:12-14](../../hi-mcp/hi-mcp-poc-json/server.ts#L12-L14), [page-bridge.ts:29-50](../../hi-mcp/hi-mcp-poc-json/page-bridge.ts#L29-L50)). Both pages reconnect after a close ([browser-bridge.ts:149-155](../../hi-mcp/hi-mcp-poc-json-client/browser-bridge.ts#L149-L155)). Since the browser chat makes independent MCP requests (sibling repo `ligna-store/hi-mcp/chat.ts:55-64`), neither chat is bound to its own planner: a call can land in the other tab. **The previous analysis wrongly treated manually adding session names as satisfying this request.**
2. `npm run plan:gpt5.4` starts the example HTTP server on **3000**, the MCP server on **3100**, and the optional chat server on **3200** ([start.mjs:38-53](../../minimal-hi-example/start.mjs#L38-L53), [start.mjs:237-249](../../minimal-hi-example/start.mjs#L237-L249)). The supplied store URL points `mcp_server` at `http://localhost:3000/`; its chat therefore fetches `http://localhost:3000/mcp` instead of the MCP service (sibling repo `ligna-store/hi-mcp/chat-options.ts:38-41`, `ligna-store/hi-mcp/chat.ts:59-64`). The example static server does not serve `/mcp` ([start.mjs:126-160](../../minimal-hi-example/start.mjs#L126-L160)). That explains the observed `Failed to fetch`; no live reproduction was run. Changing the URL to port **3100** is necessary but insufficient: the example launcher defaults `HI_MCP_PAGE_ORIGINS` to its own origin only, excluding `https://www.roomle.com` ([start.mjs:168-173](../../minimal-hi-example/start.mjs#L168-L173)), and even with that origin allowed, one `PageBridge` would still mix the two apps.
3. The store creates its browser bridge and chat independently, without waiting for a server acknowledgement that this page owns the session (sibling repo `ligna-store/components/blocks/Planner.vue:250-271`). Browser `fetch`/WebSocket failures and denied local-loopback permission must also leave chat unusable with actionable status, not an enabled chat that later reports only `Failed to fetch`.

## Proposed Behavior

1. **Cloudflare: automatic isolation.** When the store URL has no `mcp_session`, generate a unique ID for this page instance on load and pass the **same** ID to its `/bridge?session=...` WebSocket and `/mcp?session=...` browser chat. A second tab, including on another device, gets a different container without a URL change. Preserve an explicitly supplied `mcp_session` for agents intentionally connecting to a known session; never silently let two pages sharing one explicit session take over from each other. Cloudflare already routes named sessions ([worker.ts:11-22](../../hi-mcp/cf/src/worker.ts#L11-L22)), so this does not require another server process. It does require capacity planning: the current deployment permits at most **five** active containers ([wrangler.jsonc:6-13](../../hi-mcp/cf/wrangler.jsonc#L6-L13)); a sixth must receive a clear unavailable status instead of a working-looking chat. Session IDs route traffic but are not authentication.
2. **Local: fail closed on a second page.** Keep one planner per local server for now. On a second page's `hello`, reject **the newcomer** with an explicit `session in use` close reason while leaving the incumbent and its pending calls alone. The browser bridge must acknowledge acceptance (WebSocket `open` alone does not prove ownership), propagate occupied/disconnected/unreachable states to the chat UI, stop retrying on occupation, and allow retry after the incumbent leaves. Disable chat submission unless this page is the acknowledged owner. Critically, `/mcp` tool calls from a browser chat must carry the page identity and the server must reject a call whose identity is not the active page's; UI-only disabling would still permit calls to affect someone else's plan during races or disconnects. External MCP clients without a page identity need an explicit policy rather than being silently attributed to a different page.
3. **Wrong endpoint and origin:** Show a connection error inside the disabled chat when the URL is port 3000 instead of 3100, the server is unreachable, the browser blocks loopback access, or the page origin is not allowed. The server should report the actual reason where possible; a browser network/CORS failure cannot always reveal which of these occurred, so the UI should offer the correct endpoint and an actionable connection check instead of asserting "occupied". To try the store locally, use `mcp_server=http://localhost:3100/` and explicitly include the store origin in `HI_MCP_PAGE_ORIGINS` alongside the example origin. `localhost` on a second device refers to that second device, not the machine hosting the example.

Running several local server processes on separate `HI_MCP_PORT` values is already supported ([server.ts:18](../../hi-mcp/hi-mcp-poc-json/server.ts#L18)), but **telling users to run another server or manually choose a session is not the feature requested**. The intended default is two independent cloud chat windows; the intended local fallback is a clearly disabled second chat.

## Scope and Checks for Implementation

- Store (sibling repo): `hi-mcp/chat-options.ts`, `hi-mcp/browser-bridge.ts`, `hi-mcp/chat-window.ts`, `components/blocks/Planner.vue` and their tests: shared automatic page ID, bridge acceptance/connection state, and disabled chat with a concrete error and retry.
- Server: `hi-mcp/hi-mcp-poc-json/page-bridge.ts`, `server.ts`, `hi-mcp-server.ts`/planner dispatch as needed for page-bound tool calls; update `hi-mcp/hi-mcp-poc-json-client/browser-bridge.ts` and the minimal example bridge consistently. Keep Cloudflare's named-session router; check capacity handling and update `hi-mcp/docs/hi-mcp-behaviour.md` when server feedback changes. Update the setup and client docs after implementation.
- Verify two otherwise identical Cloudflare store URLs on separate tabs/devices control distinct plans; a deliberate same-session collision cannot hijack either plan; and an occupied local server, an unreachable URL and port 3000 each leave the second chat disabled with useful feedback. No tool call may mutate a planner belonging to another tab, including during reconnects.

## Outcome

The store now generates one container session and a separate browser caller ID per page, reusing
an explicit `mcp_session` when supplied. The server acknowledges only an accepted page, refuses a
newcomer with WebSocket 4409, returns HTTP 409 for a browser ID that does not own the planner, and
rechecks ownership on planner calls. The chat disables submission until acknowledgement, displays
connection and occupied errors and provides a retry button. `npm run mcp-server` at the example
repository root starts only the MCP server. Unit tests and a live local WebSocket/HTTP probe
confirmed a 200 owner request, a 409 newcomer request and the 4409 close without replacing the
owner. Live Cloudflare two-tab and deployed-store browser checks remain to be run after deployment;
the five-container limit still applies.
