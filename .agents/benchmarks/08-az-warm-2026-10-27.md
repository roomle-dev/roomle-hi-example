## Executive summary

On the build with the library read before the first prompt, **every page reads the planner's library context once the catalog has loaded and before the prompt**: 729–754 ms in the planner on all six pages, the assistant's console line "library read before the first prompt: 111 articles in 731–764 ms". **The first turn's library read is then warm**: 6.3–8.4 ms in the planner, the reference acquired in 18.1–24.3 ms (06: 14.6–31.8 ms), the first request 0.033–0.045 s after the turn start. On the build of 07, with the runner's wait no longer calculating the templates, the same first turn reads the library for 755 / 781 ms, acquires its reference in 772 / 798 ms and sends its first request **0.783 / 0.809 s** after the turn start — what the ligna-store and the example's chat window paid on the first prompt of a page, and what the read before the first prompt takes away. The creations keep the shape of 06 and 07 — the skills at call 1, the create at call 2, 6 / 6 calls for the image kitchen, 3 / 3 for the text kitchen — with the kitchens of 06: the first kitchen comes after **25.931 / 30.252 s** (image, mean 28.091 s; 06: 29.654 s) and **26.455 / 28.954 s** (text, mean 27.705 s; 06: 30.287 s), within the spread of 06, as expected, since 06's runner had calculated the templates before its prompts. The page is ready after 4.9–5.9 s (06: 5.0–7.7 s). **The library read before the first prompt is accepted**: criteria 1 to 4 hold.

## How it was measured

The collector of report 07, regenerated from the current [prompt runner](../scripts/run-hi-mcp-prompt.js): in the example page, the hook marks every fetch whose path ends in `/v1/responses` (start, response headers, the end of the stream read through a clone, request bytes, the `reasoning` object and the input items of the body), the tool bridge `callExternalObjectAgentTool` (start, end, result bytes) and every output part the window receives; in the planner frame, it wraps the seven planner methods of `window.RoomlePlanner` from the page load on and timestamps the `[hi-mcp]` log lines. Turn start and end are taken around `onPlanningAssistantPrompt`. All marks are `performance.timeOrigin + performance.now()`. No response routing is used, so the browser's HTTP cache works as usual.

Three changes for 08, so that the page reads its library as in the hosts:

- **The runner's wait for the catalog calculates no template.** The prompt runner waits until `getExternalObjectLibraryContext` lists articles, and that read calculates the article templates before the first prompt — in every run of 01–07 and of "test the mcp". The runner of 08 asks with an empty list of article ids, which lists the catalog without calculating a template (4 ms), so the page's first full read is the assistant's.
- **The prompt comes 5 s after the page is ready**, a user's time to type, so that a read still running does not decide the measurement. The milestones from the recorded run start and from the subprocess start contain the 5 s; the page-ready milestone does not.
- **The timeline carries** the page's time origin, the time the example page reports the plan's groups loaded (`hiPosGroupsCompletelyLoaded`) and the assistant's console line on its library read before the first prompt.

All four paid runs completed without provider or chat errors, retries or snapshot failures; no run is excluded. The four invalid-key checks ended as intended, with the first request rejected at HTTP 401 and no inference. No page sent a model request before its prompt. The backsplash calculation failure of the image runs is tool feedback, separate from chat success.

**The read before the first prompt takes the templates out of the first turn.** On the build of 07 the first turn's library read is the page's first full read: the planner calculates the 111 article templates in it (755 / 781 ms), the plan state read waits for it in the tools' queue (769 / 794 ms), and the first request leaves 0.783 / 0.809 s after the turn start. ## How to read the step deltas

Start/End are seconds relative to the assistant turn start. Delta is elapsed time, rounded to three decimals; the elapsed-ms columns keep short calls. A model call ends when its response stream ends, measured through the clone; its start is that end minus the SDK's response duration, so the start is derived. Model duration includes transport, provider work and streaming. Tool wall time is the union of parallel intervals; the two bootstrap reads of a turn run in parallel before its first request. A nested planner call belongs to the tool of the last `[hi-mcp] tool` line before its own `[hi-mcp] call` line in the planner frame. Planner calls without such a line are the planner's own price refresh after a plan change, listed apart. A window update is any output part the window receives: a status (`activity`) or a piece of answer text. Runner start follows browser launch; subprocess time includes launch and shutdown.

## Proposed experiments and rejected conclusions

- Whether the read before the first prompt holds back the plan's load: the time to the loaded plan on more pages with and without the read, or the read started only once the plan's groups are loaded — a signal of the host page the assistant does not receive today. Criterion 3 does not ask for it.
- Text run 1 created 11 root modules against 13–14 in 06, the same L-shaped kitchen with fewer units on the back wall — the model's planning, which the library read does not touch.
- The seconds of the creations are not F's measure: 06's runner had calculated the templates before its prompts, so 08 against 06 shows that the hosts now get 06's first turn, not a gain over it; the first-kitchen differences are within 06's spread. The first read of a page is F's measure.

## Measurement gaps and open work

- Kitchen completion is a conservative loaded-plan milestone, not the first painted frame; a window update is the output part the window receives, not its painted frame.
- Provider queueing, prefill, reasoning, generation, network and kernel or render work are not separated.
- That the planner's view does not react during the read before the first prompt follows from the synchronous calculation; no frame was measured.
- The time the plan's groups are loaded is the example page's callback, two to four pages per build; it does not separate the planner's load from the read before the first prompt that runs beside it.
- One library: Furniture_Smith with 111 articles, all without docking vectors of their own.
- Two repetitions per test give observed values and ranges, not a p95; the provider cache state differs between the runs.
