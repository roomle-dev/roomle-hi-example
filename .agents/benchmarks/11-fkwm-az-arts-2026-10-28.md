## How it was measured

A copy of [run-hi-mcp-prompt.js](../scripts/run-hi-mcp-prompt.js), written by the session's make-timing-runner.mjs, retained its normal prompt, usage, tool, plan and snapshot collection and added timestamp-only hooks with a Playwright init script. No productive file was modified, and no response routing was used, so the browser's HTTP cache works as usual.

- The assistant's existing diagnostics supply per-call response duration, time to first output, reference acquisition, first visible text, tokens, cache counters, request bytes and full-turn duration.
- Browser events mark turn start and end around onPlanningAssistantPrompt, each model fetch (start, response headers, the end of the stream read through a clone), tool forwarding start/end through callExternalObjectAgentTool, every output part of the window, and every planner-method start/end in the planner frame with its [hi-mcp] log line.
- Browser timestamps use performance.timeOrigin + performance.now(), so the host and iframe share an epoch. Tables use seconds relative to assistant turn start.
- Tool result sizes are UTF-8 bytes of JSON.stringify(result), including the MCP wrapper and base64 image content where present. They are not model tokens or compressed HTTP bytes.
- Nested planner calls are attributed by the [hi-mcp] tool and call log lines; the two reads before the first request run in parallel and are told apart by their planner method. Tools a model response sends together run in the planner one after another; their planner calls would be attributed by that order, each plan-changing tool ending with its feedback or error line — no response of these runs sent two planner tools together, so the rule did not apply. Nested planner time is included in tool time. Overlapping tools are counted once for wall time. Model/tool overlap is measured from intervals and subtracted once; it is 0.000 s / 0.000 s here.
- Recorded run start is the runner's runSession start, after browser launch. The subprocess measurement also includes browser launch, output writing and browser/launcher shutdown. Its result is distinct from the recorded ready + chat + snapshot phases.
- The runner waits until the library context lists articles before it sends the prompt, and the assistant reads the library before the first prompt itself; both reads calculate the article templates. The reads of the turn are therefore warm, as in the hosts.

Both turns completed without provider/chat errors, retries or excluded attempts, and both saved a plan.

## How to read the step deltas

**Agent/model delta s** is how long the model call takes to return its decision, tool arguments or text. It includes the provider round trip and stream handling. **Tools delta s** is the time spent executing that step's tools, counting parallel calls once. **Total step delta s** runs from the start of the model call until its tools complete; the last step ends when the assistant turn completes. The difference includes local handling within the step. Small gaps between steps and the initial reads of the library reference and the plan state are outside these step totals.

The **Start s** and **End s** columns are timestamps measured from assistant turn start; they are not durations. In the detailed call tables, **Delta s = End s − Start s** is the duration of that individual call. Tool/planner tables retain milliseconds as additional detail.

## Findings and the evidence behind them

### 1. Every request carries the shortened catalog

The shared reference is **11,134 bytes** smaller than the baseline's and the library reference **11,162 bytes** smaller. Every request of both runs carries **2,587 input tokens** less: the first call 65,651 against 68,238, and each later call by the same amount. Over the turn the runs send 219,793 / 220,838 input tokens against 229,636 / 229,214. The difference is the shortening less the library's additions (11,010 against 585 bytes of raw JSON); the tokens of the two are not measured apart. Of those input tokens 91.91% / 95.43% come from the cache, against 95.15% / 95.33% in the baseline.

### 2. The later first kitchen comes from the provider, before the create

Of the 27.838 s to the first kitchen in the mean (the baseline: 23.980 s), the skill call and the reads before the create take 5.301 / 5.847 s against 3.196 / 1.963 s. The skill call is the same request in all four runs — 22 output tokens, no reasoning, 2,587 input tokens fewer here —; run 2 waits **5.250 s** for the response headers (the baseline: 2.475 / 1.528 s), run 1 receives its first output after 2.034 s and the end of the stream 3.238 s later. The create call takes **21.545 / 15.913 s** (17.615 / 18.714 s), **15.581 / 10.969 s** until its first output (10.132 / 11.346 s), with 327 / 203 reasoning tokens (229 / 220); of the 29.381 / 26.296 s to the first kitchen it is 73% / 61%. None of these waits is a function of the catalog; two runs do not separate them from the provider's spread.

### 3. Information gathering stays cheap; no call reads the catalog

The library reference and the plan state are read in parallel before the first request: **15.8 / 16.8 ms** in run 1 and **21.3 / 23.0 ms** in run 2 as tools. All information tools of a turn take **17.8 / 23.7 ms** in union. No model call requests `get-plan-context`, and none asks for article details.

### 4. The kitchen is the requested one, with other articles

Both snapshots contain an L-shaped kitchen around the back right corner at [4815, 3765, 0] with **rotationZ = 270°**, around the corner unit UERTB90, with walnut fronts 215 in the Nature program and the dark marble worktop 324, as in the baseline: run 1 with 12 root modules, run 2 with 14 (the baseline: 14 / 13). Run 1 takes SUBA60 for the sink, a unit with a fixed front and a pull-out whose drainer reaches over the unit on its right; run 2 keeps SUT60, whose new library text puts the drainer over the unit on its left. In both runs the drainer reaches over a storage base unit, not over the hob — run 1's over the drawer unit US2A90, run 2's over the door unit UTB60 —, and both take HK260, the fridge/freezer housing, where the baseline took HK60. The catalog lines of SUBA60 and SUT60 are among the 19 shortened descriptions, and both carry the library's new sink texts; the runs do not tell which change made the choice. No create result names an obstacle or a correction. The top views were inspected; the fronts look light there, the renderer's top light.

## Measurement gaps and open work

- **First painted frame:** no GPU presentation/paint marker was captured. Create-tool completion is an upper bound for a loaded kitchen; first visible geometry could appear earlier within the 2.534–4.536 s create.
- **Provider internals:** model time combines network, queueing, input processing, reasoning, generation and SDK stream handling. Time to first output does not isolate prefill; response-header time does not isolate network RTT.
- **Tool internals:** the planner table separates planner access from the surrounding tool, but does not profile every individual filtering, projection, docking, library-calculation or kernel-load function. Remaining tool time must not be renamed CPU assembly time.
- **Final text start:** first visible text refers to the first planning preamble; the end of the turn marks completion of the final answer. Final-answer text-delta start was not separately instrumented.
- **Startup attribution:** page/module/library/plan/assistant initialization, the runner's readiness read and the assistant's library read before the first prompt overlap inside the ready phase. They were not profiled individually.
- **Instrumentation overhead:** extra console events, UTF-8 size measurement and log delivery add unquantified overhead; both runs have the same hooks. The planner is a Vite development server; do not use these page-startup numbers as production cold-start numbers.
- **Sampling:** two runs establish a repeated measurement and show the variation of single calls. They do not establish a p95, a stable service-level expectation or the cause of provider variability. Another pair costs about 2 minutes and 0.4M input tokens, most of them read from the cache.
- **Library change:** the library changed between the baselines and this capture (see [What changed besides the code](#what-changed-besides-the-code)). The token difference is measured as a sum; no control run of the old planner on today's library separates the two changes in tokens, seconds or the articles chosen.
